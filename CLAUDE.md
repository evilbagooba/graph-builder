# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

tako-nerve (formerly Graph Builder): the idea-graph tool of the tako suite. A node/edge diagram editor with a library of projects. A static React + Tailwind v4 page built by Vite, with **no server of its own**: projects come from the tako hub when one is running, or from a file when not. (It used to have a Node server and a SQLite database; both are gone. An old `data/app.db` may still sit in a checkout, git-ignored and unused.)

Planned work, decisions and known open bugs are in `ROADMAP.md`; keep it current as items land.

## Commands

- `npm run dev` — Vite dev server on :5173.
- `npm run typecheck` — type-checks the client (`client/tsconfig.json`) and the tests (`test/tsconfig.json`). There is no linter.
- `npm test` — contract tests (`test/*.test.ts`, Node's built-in test runner via `tsx`): every fixture project shipped with `tako` must still open and save; run one with `npm test -- --test-name-pattern="sourdough"`.
- `npm run build` — Vite build into `client/dist`, then `scripts/check-size.mjs` fails it if the gzipped first-load JS/CSS exceed their budgets (raise a budget deliberately, not to get a build through). Chunks loaded on demand are reported but not budgeted.
- `npm run preview` — serve the build.
- To try it against a hub without touching real projects: in the tako repo, `node bin/tako.mjs --dir /tmp/x --port 4199`, then open the app with `?hub=http://localhost:4199`.

## Architecture

**`tako`: the project format, operations layer and hub — a separate repo.** It lives at github.com/evilbagooba/tako and is pinned by tag in `package.json` (`"tako": "github:evilbagooba/tako#vX.Y.Z"`), shipped as TypeScript source that Vite and tsx compile. Don't edit `node_modules/tako`: change the tako repo (its own tests cover ops, history, fixtures and the hub), tag a release, then bump the pin here. Entry points: `tako/model` (zod-free: types, ops, `reviewOps`, `ProjectStore`, `createLocalStore`) and `tako/client` (zod-free: `connectHub`), which are what the page imports statically; and `tako` (adds the zod schemas, `migrateProject`, `parseOps`), which only tests import statically. In the page, `tako` is reached only through `await import("tako")` (in `client/src/file.ts` and the chat drawer's fallback), so zod (~27 kB gzip) loads on demand and stays out of the first-load bundle. A project is one versioned JSON document (`schemaVersion`), stored by the hub as `<id>.tako.json`. Nodes have `shape` (circle/emoji/image, the visual form) and `kind` (a semantic tag like "centre"/"foil"), plus `provenance`, and projects have `work`, `artifacts` and `narratives`. A new op is added in the tako repo (its case in `applyOp`, `opSchema` and `describeOp`), released, then used here.

**Where a project lives: hub or file, behind one interface.** `App` looks for the hub once on load (`connectHub`, default `http://localhost:4100`, `?hub=` to override). With a hub, `Library` lists its projects (`useProjectList`, refreshed by hub events) and create / import / example / duplicate / delete go through it; an opened project is `hub.open(id)`, a `ProjectStore` kept in step with every other tool (edits are sent as ops, the hub answers with the whole project, changes made elsewhere arrive live, undo is the hub's shared history). Without a hub, a project is a `createLocalStore` over an opened or new file, saved on request with Ctrl+S (`saveToFile`; `file.ts`). Both arrive at the `Editor` as an `OpenProject` (`store`, `hub`/`hubId` or `file`). `?project=<id>` in the URL reopens a hub project on reload. Never talk to the hub from inside the editor except through the store, plus `hub.checkOps`, `hub.create` (duplicate) and `hub.remove`.

**Client: nearly everything is in `client/src/App.tsx`.** `Library` (list/create/import), `Editor` (SVG canvas), `NodePanel`/`EdgePanel` (detail sheet). Node shapes (`shape`): `circle`, `emoji`, `image` (images are an http(s) URL or a downscaled `data:image/...` upload stored inline in the document). Edge endpoints are computed by `borderPoint`, which is shape-aware.

**Editor layout: full-bleed canvas with floating islands.** The canvas fills the editor, and the chrome floats on it as small `.gb-island` panels: graph menu top-left, tools bottom-centre, zoom bottom-left (top-right on narrow screens), legend panel toggled from the tools, and the connect prompt above the tools. The editor panel (`InspectorPane`) has three modes: `floating` (wide default, shown only while something is selected, closed with Esc), `docked` (opt-in pin, remembered in localStorage, takes its own column) and `sheet` (narrow screens). Every floating panel declares the canvas edge it covers with `data-viewport-ui="top|right|bottom|left"`. `visibleArea()` subtracts those, and fit, zoom, keep-selection-in-view and new-node placement all use the visible area. A new floating panel must carry `data-viewport-ui`, or the graph will be framed underneath it. Ctrl/Cmd+. toggles focus mode, which hides all chrome. The zoom % readout is written by `setCamera`, not rendered.

**Edits go through `dispatch(ops)`; undo belongs to the store.** The `Editor` reads the project with `useSyncExternalStore(store.subscribe, store.get)`, and every change is `dispatch`ed as ops (tako's `Op` union) into `store.dispatch`: never edit `nodes`/`edges`/`title` directly, and add a new op to tako (and release it) rather than special-casing the UI. `historyRef.current.present` is a getter for the store's latest project, for handlers that run between renders. Edits sharing a `coalesceKey` within a second merge into one undo step (typing a title, nudging with arrows). A node drag calls `store.preview()` per frame (local only, nothing is sent) and `store.commitPreview()` on release, so it's one undo step and one edit on the wire. View state (camera, selection, panels) is never an op. Undo/redo (`store.undo()` / `store.redo()`): Ctrl/Cmd+Z, Ctrl/Cmd+Shift+Z or Ctrl+Y, and buttons in the menu island; text fields keep the browser's own undo. With a hub, undo is asynchronous and shared: it can undo a change made in another tool. The header's save label comes from `snap.sync` (hub) or from comparing the project with the last one saved (file). An edit the hub refuses, or that no longer applies after someone else's change, surfaces as a notice through `open.rejected`.

**Suite slots: work, paths, chat.** `WorkSection` (in `NodePanel`) edits a node's work items via `spawn_work`/`update_work`/`remove_work`. The Legend, Paths and Chat panels share the left side (one open at a time; on phones they're top-anchored, fold into a "Panels" menu in the toolbar, and declare `data-viewport-ui="top"`). Path mode: while `activePathId` is set, `tapNode` toggles the node as a stop (`reorder_narrative`) instead of selecting it. Empty paths are never kept: "+ New path" is a `draftPath` (view state) until its first stop creates it, leaving a path that's been emptied removes it, and any left by an older version are removed when the project opens; `PathOverlay`/`PathBadges` draw the route and `.gb-path-mode` dims the rest. The chat drawer keeps its messages as session view state; a proposal is applied only by the user, as one `dispatch` (one undo step), after re-checking it against the current project. Pasted op lists are validated by `hub.checkOps`, or by `parseOps` loaded on demand when there is no hub.

**Legend.** Each graph document has a `legend` map from option keys (`color:teal`, `size:xl`, `dimmed`, `edge:dashed`, `arrow:both`) to the meaning the author gave it. `legendGroups()` lists only options the graph actually uses, and `swatchMarkup()` is the single swatch renderer shared by the on-canvas `LegendCard` and the SVG/PNG export. Meanings are set with the `set_legend` op; an empty meaning removes the entry.

**UI components: native HTML, no component library.** `client/src/ui.tsx` holds small primitives built on platform elements: `Button`, `TextField`/`Textarea` (label + input, hidden labels via Tailwind's `sr-only`), `ChoiceGroup` (a `<fieldset>` of real radios drawn as a segmented control or colour swatches), `Switch` (`role="switch"` checkbox), `Dialog` (`<dialog>` + `showModal()`), `Menu` (Popover API; JS only for placement and arrow-key roving), and a `toast()` queue with an always-mounted `<Toaster/>` live region. Icon-button tooltips are CSS-only via `data-tip`. Their styles live in the "UI primitives" section of `theme.css`, inside `@layer components`, so Tailwind utilities passed through `className` still win. Add new controls the same way, native element first. Reach for a dependency only for genuinely hard widgets, and then an unstyled one (e.g. a single React Aria component), never a styled kit. Notices go through `toast` via `setNotice` in the `Editor`, which replaces rather than stacks them. Never declare transitions on `*` or set `interpolate-size` globally: blanket transitions turn every per-frame SVG geometry change on the canvas into a CSS transition and lag pans and drags (this happened with Kernel UI's reset, which is why the app no longer uses Kernel).

**Canvas interaction and rendering performance.** The camera (`{x, y, k}`) is deliberately *not* React state: it lives in `cameraRef`, and `setCamera` writes the transform straight onto the canvas `<g>`, so pan, pinch, wheel, coast (`coast`) and the zoom/fit spring (`moveCamera`) never re-render anything. Read the camera from `cameraRef`, never from state. New input or `stopCameraAnim` cancels any running animation. Node drags *are* React state; they're queued and applied once per frame with `flushSync` (`queueFrame`/`flushFrame`), because a plain setState from a rAF callback renders after the paint and visibly lags. `NodeView`/`EdgeView` are memoized and receive stable handlers via refs, and everything outside the canvas (header, zoom controls, legend, inspector, dialog) is memoized against what it shows. Keep new props stable, or drags and pans will start re-rendering the whole editor again. The wheel listener is attached natively (non-passive) so trackpad pinch (ctrl+wheel) can be intercepted. `prefersReducedMotion()` switches animations off; matching CSS lives in `client/src/theme.css`.
