# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Graph Builder: a node/edge diagram editor with a library of saved graphs. React + Tailwind v4 client built by Vite, a Node server using SQLite (better-sqlite3 + drizzle-orm). It began as a Muse/Hatch "web artifact" and was ported to run standalone; the original Muse version is not maintained here.

Planned work, decisions and known open bugs are in `ROADMAP.md`; keep it current as items land.

## Commands

- `npm run dev` — Vite dev server on :5173. The `/actions` API runs inside it (see `vite.config.ts`), and server code hot-reloads.
- `npm run typecheck` — type-checks the client (`client/tsconfig.json`), the server (`server/tsconfig.json`) and the tests (`test/tsconfig.json`). There is no linter.
- `npm test` — contract tests (`test/*.test.ts`, Node's built-in test runner via `tsx`): every fixture project shipped with `core` must still open and save; run one with `npm test -- --test-name-pattern="sourdough"`.
- `npm run build` — Vite build, then `scripts/check-size.mjs` fails it if the gzipped JS/CSS exceed their budgets (raise a budget deliberately, not to get a build through).
- `npm start` (after a build) — production: `server/src/main.ts` (run via `tsx`) serves `client/dist` plus `/actions`. Env: `PORT` (3000), `DATA_DIR` (`./data`).

## Architecture

**Typed RPC, no codegen.** `server/src/actions.ts` exports `Actions`, built with `defineAction` from `server/src/rpc.ts` (zod request/response schemas + `handler(ctx, args)`). `server/src/http.ts` handles `POST /actions` with body `{ action, args }`: it parses args through the action's zod request schema (this is where defaults get applied), runs the handler, and replies `{ ok, result | error }`. `client/src/api.ts` builds `api` via `createActionClient<typeof Actions>()` using a *type-only* import of the server module (`verbatimModuleSyntax` makes dropping `type` a compile error — keep server runtime out of the client bundle). Graph data types (`ProjectNode`, `ProjectEdge`, aliased `GraphNode`/`GraphEdge` in `App.tsx`) come from `core`; response types come from `ApiResponse<typeof api, …>`.

**`core`: the project file format and operations layer — a separate repo.** It lives at github.com/evilbagooba/core and is pinned by tag in `package.json` (`"core": "github:evilbagooba/core#vX.Y.Z"`), shipped as TypeScript source that Vite and tsx compile. Don't edit `node_modules/core`: change the core repo (its own tests cover ops, history and fixtures), tag a release, then bump the pin here. Two entry points: `core/model` (zod-free: types, ops, history, `reviewOps`), which is what the browser imports, and `core` (adds the zod schemas, `migrateProject`, `parseOps`), which only the server and tests import, keeping zod (~25 kB gzip) out of the client bundle. A project is one versioned JSON document (`schemaVersion`), and the same document is stored in SQLite (one `graphs` row: title + `data`), exported as a file, and imported via the `importProject` action. Nodes have `shape` (circle/emoji/image, the visual form) and `kind` (a semantic tag like "centre"/"foil", reserved), plus reserved `provenance`, and projects have reserved `work`, `artifacts` and `narratives`. New fields use `.default(...)` so older documents still validate; breaking changes bump `SCHEMA_VERSION` and add a step to `migrateProject`, which the server runs on every read and import (v0 → v1 moved the shape out of `kind`). `normalizeProject` drops dangling references on save. Ops from outside the UI (chat, other tools) are validated with `opSchema`/`parseOps` (server: the `checkOps` action; patch schemas carry no defaults, since a default would overwrite stored values) and described for review with `reviewOps`. A new op is added in the core repo (its case in `applyOp`, `opSchema` and `describeOp`), released, then used here. Table changes need a new SQL file in `drizzle/` plus a `meta/_journal.json` entry with a `when` greater than the previous one.

**Client: nearly everything is in `client/src/App.tsx`.** `Library` (list/create/import), `Editor` (SVG canvas), `NodePanel`/`EdgePanel` (detail sheet). Node shapes (`shape`): `circle`, `emoji`, `image` (images are an http(s) URL or a downscaled `data:image/...` upload stored inline in the document). Edge endpoints are computed by `borderPoint`, which is shape-aware.

**Editor layout: full-bleed canvas with floating islands.** The canvas fills the editor, and the chrome floats on it as small `.gb-island` panels: graph menu top-left, tools bottom-centre, zoom bottom-left (top-right on narrow screens), legend panel toggled from the tools, and the connect prompt above the tools. The editor panel (`InspectorPane`) has three modes: `floating` (wide default, shown only while something is selected, closed with Esc), `docked` (opt-in pin, remembered in localStorage, takes its own column) and `sheet` (narrow screens). Every floating panel declares the canvas edge it covers with `data-viewport-ui="top|right|bottom|left"`. `visibleArea()` subtracts those, and fit, zoom, keep-selection-in-view and new-node placement all use the visible area. A new floating panel must carry `data-viewport-ui`, or the graph will be framed underneath it. Ctrl/Cmd+. toggles focus mode, which hides all chrome. The zoom % readout is written by `setCamera`, not rendered.

**Edits go through `dispatch(ops)`; undo comes from history.** The `Editor` holds the project in a `History` (core's history module) mirrored in `historyRef`, and every change is `dispatch`ed as ops (core's `Op` union): never edit `nodes`/`edges`/`title` state directly, and add a new op to core (and release it) rather than special-casing the UI. Edits sharing a `coalesceKey` within a second merge into one undo step (typing a title, nudging with arrows). A node drag uses `preview()` per frame and `commitFrom()` on release, so it's one undo step. View state (camera, selection, panels) is never an op. Undo/redo: Ctrl/Cmd+Z, Ctrl/Cmd+Shift+Z or Ctrl+Y, and buttons in the menu island; text fields keep the browser's own undo. Autosave debounces ~600 ms and sends the whole project via `saveGraph`; every save also writes the query cache so reopening never loads a stale copy, and a pending save is flushed on leaving. A save the server rejects surfaces as a notice and stops autosave until fixed, which is why `NodePanel` only commits complete image links.

**Suite slots: work, paths, chat.** `WorkSection` (in `NodePanel`) edits a node's work items via `spawn_work`/`update_work`/`remove_work`. The Legend, Paths and Chat panels share the left side (one open at a time; on phones they're top-anchored, fold into a "Panels" menu in the toolbar, and declare `data-viewport-ui="top"`). Path mode: while `activePathId` is set, `tapNode` toggles the node as a stop (`reorder_narrative`) instead of selecting it. Empty paths are never kept: "+ New path" is a `draftPath` (view state) until its first stop creates it, leaving a path that's been emptied removes it, and `withoutEmptyPaths` filters what's saved and loaded; `PathOverlay`/`PathBadges` draw the route and `.gb-path-mode` dims the rest. The chat drawer keeps its messages as session view state; a proposal is applied only by the user, as one `dispatch` (one undo step), after re-checking it against the current project.

**Legend.** Each graph document has a `legend` map from option keys (`color:teal`, `size:xl`, `dimmed`, `edge:dashed`, `arrow:both`) to the meaning the author gave it. `legendGroups()` lists only options the graph actually uses, and `swatchMarkup()` is the single swatch renderer shared by the on-canvas `LegendCard` and the SVG/PNG export. Meanings are set with the `set_legend` op; an empty meaning removes the entry.

**UI components: native HTML, no component library.** `client/src/ui.tsx` holds small primitives built on platform elements: `Button`, `TextField`/`Textarea` (label + input, hidden labels via Tailwind's `sr-only`), `ChoiceGroup` (a `<fieldset>` of real radios drawn as a segmented control or colour swatches), `Switch` (`role="switch"` checkbox), `Dialog` (`<dialog>` + `showModal()`), `Menu` (Popover API; JS only for placement and arrow-key roving), and a `toast()` queue with an always-mounted `<Toaster/>` live region. Icon-button tooltips are CSS-only via `data-tip`. Their styles live in the "UI primitives" section of `theme.css`, inside `@layer components`, so Tailwind utilities passed through `className` still win. Add new controls the same way, native element first. Reach for a dependency only for genuinely hard widgets, and then an unstyled one (e.g. a single React Aria component), never a styled kit. Notices go through `toast` via `setNotice` in the `Editor`, which replaces rather than stacks them. Never declare transitions on `*` or set `interpolate-size` globally: blanket transitions turn every per-frame SVG geometry change on the canvas into a CSS transition and lag pans and drags (this happened with Kernel UI's reset, which is why the app no longer uses Kernel).

**Canvas interaction and rendering performance.** The camera (`{x, y, k}`) is deliberately *not* React state: it lives in `cameraRef`, and `setCamera` writes the transform straight onto the canvas `<g>`, so pan, pinch, wheel, coast (`coast`) and the zoom/fit spring (`moveCamera`) never re-render anything. Read the camera from `cameraRef`, never from state. New input or `stopCameraAnim` cancels any running animation. Node drags *are* React state; they're queued and applied once per frame with `flushSync` (`queueFrame`/`flushFrame`), because a plain setState from a rAF callback renders after the paint and visibly lags. `NodeView`/`EdgeView` are memoized and receive stable handlers via refs, and everything outside the canvas (header, zoom controls, legend, inspector, dialog) is memoized against what it shows. Keep new props stable, or drags and pans will start re-rendering the whole editor again. The wheel listener is attached natively (non-passive) so trackpad pinch (ctrl+wheel) can be intercepted. `prefersReducedMotion()` switches animations off; matching CSS lives in `client/src/theme.css`.
